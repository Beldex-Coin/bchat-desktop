bchat-desktop · snode_api

Zero-, one-, and three-hop onion

Two legs, every message: the sender stores it on a node in the recipient's swarm, then the recipient's app polls that node and retrieves it — both legs go through the same bchatFetch() in bchatRpc.ts, so both use whichever transport that person's own onion-routing setting picks. The message content itself is already end-to-end encrypted between the two people chatting either way — what differs below is only that transport: zero-hop (no onion layer at all — the old direct-mode behavior), one-hop onion (the current fix, encrypted straight to the node), and three-hop onion (full routing through a guard and a relay). Each row assumes both people have the same setting, just to keep one row readable — in reality each side's toggle is independent.

Zero-hop

No onion layer on either leg — the old direct-mode behavior. Plain JSON over snodeHttpsAgent with rejectUnauthorized: false: both the store and the retrieve are readable and forgeable by anyone on the network path.

One-hop onion

Same round trips as zero-hop, but each leg is now encrypted to the swarm node's x25519 key via bchatOneHopOnionFetch(), so the unverified TLS layer underneath no longer matters.

Three-hop onion

Full routing on both legs, each through its own guard and relay. Only that leg's guard node ever learns the requester's IP; the swarm node never does.
